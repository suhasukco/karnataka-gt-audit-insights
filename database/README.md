# database — shared schema package (`gt_database`)

SQLAlchemy models + Alembic migrations for the `warehouse` (analytics) and
`restricted` (PII) schemas. Both `apps/api` and `etl/` import this package
rather than defining their own models, so there's exactly one source of truth
for what the schema looks like.

`raw` and `staging` schemas are **not** managed here — they're created and
truncated by the ETL scripts on every run, since they're disposable working
tables, not a stable contract anything else depends on.

## Setup (one-time, from the repo root)

```
python -m venv .venv
.venv\Scripts\pip install -e ./database
```

Copy `.env.example` → `.env` at the repo root and set `DATABASE_URL` to your
local Postgres. See `../infra/README.md` for creating the database itself.

## Running migrations

From this folder, with the venv active:

```
alembic upgrade head        # apply all migrations
alembic downgrade base      # tear everything back down
alembic current             # what's applied right now
```

## Adding a new migration

Edit the models under `gt_database/models/`, then:

```
alembic revision --autogenerate -m "describe the change"
```

**Always read the autogenerated file before applying it** — Alembic is good
but not perfect at detecting schema changes (it won't reliably pick up on
things like server-side check constraints or column renames without a hint).

## Schema overview

- `dim_geography` — State/District/Taluk/City/Pincode hierarchy (NOT lat/long
  or street address — those live on `outlet` directly, since they're unique
  per outlet and a join would buy nothing).
- `dim_outlet_type`, `dim_channel`, `dim_outlet_class`, `dim_ownership` — small
  reference lookups.
- `dim_product_category` — the 22 real tracked categories, seeded by the
  initial migration. Carries `has_sku_count` / `has_product_type_text` /
  `flag_only` metadata since the source's 22 category columns are not uniform.
- `dim_brand` — cleaned/deduplicated brand names split out of the source's
  free-text `Brands Stocked` column.
- `outlet` — the core master record, one row per surveyed outlet (this is a
  one-time census, so there's no survey-round dimension — `outlet_id` is the
  grain of everything below).
- `fact_infrastructure`, `fact_business` — 1:1 with `outlet`, the physical
  fixtures and commerce-behaviour columns from the source.
- `fact_outlet_category` — long/narrow unpivot of the 22 category flag/SKU/
  product-type column groups (one row per outlet × category actually reported).
- `fact_outlet_brand` — outlet ↔ brand bridge table.
- `restricted.outlet_contact` — owner/contact/GST/email PII, deliberately
  isolated from `warehouse` and never joined into analytics queries.
